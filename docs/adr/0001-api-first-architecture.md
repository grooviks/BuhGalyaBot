# ADR-0001: API-first архитектура BuhGalyaBot

- Статус: принято
- Дата: 2026-09-06
- Лицо, принимающее решение: владелец проекта

## Контекст

BuhGalyaBot — личная система учёта, которой пользуются через команды Telegram.
Она должна хранить:

- долги перед пространством учёта и один или несколько частичных возвратов;
- ежемесячные регулярные и разовые сборы;
- явно заданный состав участников сбора, в том числе людей без Telegram;
- индивидуальные ожидаемые суммы и платежи участников, включая переплаты.

Данные могут изменять только Telegram-аккаунты из глобального allowlist,
который поддерживается вручную. Сначала бот обслуживает одно пространство
учёта и один чат, но в дальнейшем должен поддерживать несколько изолированных
пространств/чатов. В будущем планируется браузерный интерфейс. История данных
должна сохраняться даже после исправления или удаления операции.

## Решение

Строим модульный монолит на Python 3.14 и PostgreSQL. Бизнес-сценарии
предоставляются через внутренний REST API на FastAPI. Telegram-бот на aiogram
является клиентом API, а не местом для бизнес-логики.

Первоначальная схема компонентов:

```
Команды Telegram ─┐
                  ├─ FastAPI-приложение ─ доменные сервисы ─ PostgreSQL
Будущий браузер ──┘
```

REST API в MVP является внутренним: он не публикуется в интернете и пока не
реализует аутентификацию для браузера. Аутентификацию и авторизацию будущего
веб-интерфейса фиксируем отдельным ADR. Telegram-адаптер определяет Telegram ID
отправителя, проверяет его по глобальному allowlist и передаёт автора в API,
чтобы у каждого изменения был известен инициатор.

Для доступа к данным используем SQLAlchemy, для миграций схемы — Alembic.
`uv` — единый инструмент для управления Python-версией, создания виртуального
окружения, установки и фиксации зависимостей и запуска локальных команд.
Lock-файл коммитим в репозиторий, а Docker-образ устанавливает зафиксированные
из него зависимости. Бот, API и PostgreSQL поставляются через Docker Compose.
Денежные суммы — неотрицательные целые рубли; копейки не поддерживаются.

### Принципы модели данных

- `workspace` владеет всеми данными учёта. `chat` может быть привязан к
  пространству. Сначала создаётся одно пространство и один чат, но схема
  допускает добавление новых без миграции данных.
- `person` — переиспользуемая запись справочника внутри пространства с
  отображаемым именем и необязательной Telegram-идентичностью. Она может
  представлять человека без Telegram.
- `debt` хранит исходную сумму, а записи `debt_repayment` уменьшают текущий
  остаток. Остаток вычисляется только по неудалённым записям.
- `collection` имеет тип `monthly` или `one_time`. Для ежемесячного сбора
  создаётся отдельный период каждого календарного месяца; разовый сбор остаётся
  открытым, пока его не закроют или не архивируют.
- `collection_participant` задаёт явный список участников. В нём хранится
  целевая сумма сбора или индивидуальное переопределение цели.
- `collection_payment` фиксирует сумму, внесённую участником. Участник оплатил
  полностью, если сумма платежей достигла цели, и переплатил, если превысила её.
- Изменения и удаления — мягкие: записи хранят сведения о создании, изменении,
  удалении и авторе. Мягко удалённые записи не участвуют в текущих расчётах,
  но сохраняют основу для будущей выдачи истории.

## Последствия

### Положительные

- Браузерный UI сможет использовать стабильные API-методы и все доменные
  правила, не дублируя и не перенося логику из обработчиков Telegram.
- Тесты концентрируются на детерминированных доменных сервисах и API-контрактах;
  Telegram-парсинг остаётся тонким адаптером.
- `uv` даёт разработке, CI и Docker единый воспроизводимый набор зависимостей.
- Изоляция по `workspace` не позволит смешать данные при будущем добавлении
  нескольких чатов.
- Записи платежей и возвратов сохраняют достаточно истории для отчётов и
  восстановления после ошибочного удаления.

### Отрицательные

- В MVP появляются API-слой и контрактные API-тесты, хотя на старте Telegram —
  единственный клиент.
- Авторизация внутреннего API намеренно минимальна до появления браузерного
  клиента; в таком виде API нельзя публиковать в интернете.
- Мягкое удаление требует, чтобы каждый расчёт остатка и отчёт исключал
  удалённые записи.
- Периоды ежемесячных сборов добавляют правила жизненного цикла, которые нужно
  покрыть тестами.

## Рассмотренные альтернативы

### Хранить всю бизнес-логику в обработчиках Telegram

Отклонено. Это ускорило бы создание первых команд, но будущий веб-интерфейс
оказался бы привязан к Telegram-коду или потребовал бы рискованного извлечения
логики.

### Сделать браузерный UI в MVP

Отклонено. Команд достаточно для текущего процесса, а UI расширил бы scope
за счёт фронтенда, сессий и веб-авторизации до подтверждённой потребности.

### Хранить суммы с плавающей точкой

Отклонено. Учитываются целые рубли, а целочисленное хранение гарантирует точные
суммы и переплаты.

### Физически удалять ошибочные операции

Отклонено. Это необратимо потеряло бы нужную историю долгов и платежей и
сделало бы будущие исторические отчёты неполными.

### Единый набор данных без `workspace`

Отклонено. Ключ пространства добавляет мало сложности сейчас и исключает
инвазивную миграцию для разделения данных при поддержке нескольких чатов.

## Отложенные решения

- технология браузерного UI и схема его аутентификации;
- останется ли доступ глобальным allowlist или появятся роли для пространств;
- напоминания, кнопочный интерфейс Telegram и ввод операций задним числом;
- команда истории и формат экспорта;
- production-хостинг, резервные копии, мониторинг и публикация API.
